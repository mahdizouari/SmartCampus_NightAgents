Why JARVIS is not a "polling LLM"
v2 said JARVIS polls every 60 s and is event-driven. v3 picks one model: events + timers, with a slow safety sweep.
 Trigger                                      Example                                                  Mechanism
 Domain event                                 pre-inscription submitted, slot cancelled, student       Outbox row → worker (or Postgres
                                              replied                                                  LISTEN/NOTIFY )

 Timer                                        reminder at T-24 h, no reply after 24 / 48 / 72 h        Celery task with ETA, stored with the appointment;
                                                                                                       cancelled when state changes
 Safety sweep                                 missed event, worker restart                             Every 10 min: reconcile states vs. timers
                                                                                                       (idempotent)

Result: nothing is "waiting in memory", reminders fire on time, and the same message is never sent twice (idempotency key =
appointment_id + message_type).

THE QUESTION THE TEAM ASKED

   6       Human RH + RH Agent at the Same Time?
    VERDICT — YES, IT IS THE BEST APPROACH, ON ONE CONDITION
    Use JARVIS for the standard path and the Human RH for exceptions with explicit case ownership. Without
    ownership, the two will contradict each other (agent sends a reminder while the RH is on the phone with the student).
    With it, you get automation's speed and human judgment where it matters.

Operating rules
 1. One owner per case: case.owner ∈ {JARVIS, RH:<user>} . When RH takes a case, all automated messages for it stop.
    RH can hand it back with one click.
 2. Agent authority is bounded: JARVIS may propose, book, remind, reschedule (max 2) and release slots. It may not
    cancel a dossier, promise admission, grant exceptions or decide anything.
 3. Template-bound messages: RH approves message templates; the LLM only personalises within them (name, date,
    language register).
 4. Escalation carries context: each RH ticket includes a 5-line LLM summary + timeline, so RH never re-reads a chat.
